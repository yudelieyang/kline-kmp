# Performance measurements

## Android drag test

Measured on model V2505A, Android 16, physical display 1440 × 3168. The installed `benchmark` build is based on release, non-debuggable, and has R8 disabled. The user reported adaptive refresh mode. Each mid-run display snapshot, taken between swipes, reported `renderFrameRate 60.000004`; this does not establish the refresh rate throughout a swipe. No refresh-rate setting was changed. Power saving reported `0`, stay-awake-while-powered reported `15`, and battery status reported AC power, level 100 and status 5 (full). The user cleared background apps before the run. Per-run battery readings and complete display outputs are saved alongside each run; reported battery temperature values ranged from 322 to 325 in the raw Android output (tenths of a degree Celsius).

Command: `.\scripts\perf\drag.ps1`. Each of five rounds ran 500/8 dp, 500/2 dp, 5000/8 dp and 5000/2 dp in that order. Each run force-stopped and launched the offline benchmark mode, checked the displayed dataset count, waited, reset gfxinfo, and performed 20 alternating swipes between (300, 1600) and (900, 1600), each with 400 ms duration. The chart moved in the [trial](results/drag/trial/first-swipe.png); trial results are excluded. A display dump between swipes introduces a pause into the measured window. These are app-wide gfxinfo statistics during that window, not exclusively frames generated by the swipes.

The following values are medians across five runs, computed by `python scripts/perf/summarize_drag.py | Tee-Object -FilePath docs/perf/results/drag/summary.csv`. All individual values are in [summary.csv](results/drag/summary.csv), and the complete raw `gfxinfo.txt`, reset output, device snapshots and pre-run screenshots are in the corresponding [run directories](results/drag/). Activity records used to confirm the foreground app are kept locally only.

Live diagnostics were added and the benchmark APK was rebuilt after this drag run; the drag numbers are from the earlier benchmark APK.

## Live correctness and memory

The same device ran a rebuilt non-debuggable benchmark APK with R8 disabled and benchmark-only live diagnostic logging enabled. The normal BTCUSDT live launch was used. The command was `.\scripts\perf\live.ps1`; Jun confirmed the phone was ready and the run was requested without phone interaction. The script waited for synchronization and took two complete `dumpsys meminfo` snapshots. The host-recorded capture start times were 2026-11-03 09:11:59.2086880 and 10:12:00.0853115, both -05:00. TOTAL PSS was 107,962 KiB and 183,534 KiB respectively; `183534 - 107962` produced 75,572 KiB. Two snapshots do not establish peak use or a memory leak, and the diagnostic logging is part of this build's workload. [Raw memory outputs and timestamps](results/live-run/).

The diagnostic snapshot was taken after the ending memory capture: logcat recorded `SNAPSHOT_BEGIN` at device Unix time 1793718777.103. The snapshot contained 60 distinct consecutive closed candles. `python scripts/perf/compare_live.py` fetched and saved the Binance market-data REST response for their exact open-time range. All 60 matched in open time, open, high, low, close and base volume after parsing REST values into the same double-precision numeric representation stored by the app; there were no missing, extra or differing rows. The [comparison output](results/live-run/comparison.txt), [complete app log](results/live-run/logcat.txt), [request metadata](results/live-run/rest-request.txt) and [raw REST response](results/live-run/rest-response.json) are preserved. The REST request was made after the snapshot, so agreement does not prove every intermediate update was correct.

The diagnostic log recorded one session, one initial synchronization, zero reconnect sessions, zero resynchronizations and zero retry events; the event times are in the comparison output. All 60 compared candles opened after both the device-recorded app start and the separately recorded host launch, and all 60 were observed as accepted closed live updates after the last synchronization. This provenance count is conservative and relies on the recorded events, not a general guarantee of merge correctness. The device and host clocks did not agree when checked, so both thresholds are reported separately rather than assuming clock synchronization. No resynchronization was observed in this run; if one had occurred, candles could have come from its REST snapshot and REST agreement alone would not establish merge correctness.

Cold-start timing was not run.
